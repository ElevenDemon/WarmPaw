## 1. Executive Summary（执行摘要）

### 问题陈述（Problem Statement）

宠主因出差、旅行、加班等原因离家时，家中宠物（猫、狗、小型宠物）面临无人喂食、饮水、清洁与照看的问题；现有方案（拜托亲友、寄养、个人喂养师）存在信任缺失、服务不标准、过程不透明、沟通低效等痛点。

### 解决方案（Proposed Solution）

**暖爪**是一个基于"自营/签约喂养师团队 + AI 智能调度与客服"的宠物上门喂养平台。宠主通过小程序下单，平台 AI 智能派单，喂养师上门执行并全程录像、进出消息提醒，AI 自动生成图文喂养报告。以"信任"和"AI"为核心差异化。

**交付形态（与原型一一对应）**：官网营销落地页 ×1、宠主端原型 ×21 屏、喂养师端原型 ×9 屏、运营后台 ×16 模块。四端共用同一套设计语言与数据语义（会员、券、等级、档案、订单状态在各端同源联动）。

### 成功指标（Success Criteria / KPI · 默认值）

| 指标 | 目标（首期上线后 3 个月内） |
|------|------|
| 首期订单量 | 上线首月 ≥ 100 单，3 个月内月均 ≥ 500 单 |
| 派单成功率 | ≥ 95%（AI 派单后喂养师最终接单） |
| AI 派单人工改派率 | ≤ 10%（衡量 AI 派单质量） |
| 客诉率 | ≤ 2%（投诉订单 / 总订单） |
| 喂养报告覆盖率 | = 100%（每单必出 AI 报告） |
| AI 客服自助解决率 | ≥ 60%（无需转人工的比例） |
| 宠主复购率 | 首月下单用户 3 个月内复购 ≥ 30% |
| 喂养师审核通过率 | 目标 60%~80%（含分级审核） |
| 派单理由覆盖率 | = 100%（每单都可查看判定理由与淘汰原因） |
| 会员付费率 | ≥ 8%（月活宠主开通月度/年度会员） |
| 优惠券核销率 | ≥ 35%（领取 / 发放的券在有效期内被使用） |
| 券领取拦截准确率 | 拦截理由可复核率 = 100%（每条拦截均可追溯到具体校验项） |

## 2. User Experience & Functionality（用户体验与功能）

### 用户画像（User Personas）

1. **出差/旅行型宠主**：25-45 岁，深圳白领，养猫/狗，一年多次长短途出差或长假出行，最在意"宠物安不安全、有没有被好好照顾"。
2. **高频通勤/加班型宠主**：偶尔无法按时回家喂食，需要灵活、单次、可信任的上门服务。
3. **兼职/专职喂养师**：深圳本地，爱宠人士或宠物行业从业者，希望灵活接单增收，在意派单量、收入、接单体验。
4. **平台运营/客服/调度**：暖爪团队成员，负责审核喂养师、处理客诉、人工改派、看数据。

### 用户故事（User Stories）

**宠主端**
- 作为宠主，我想用微信快速登录并绑定手机，以便下单。
- 作为宠主，我想创建和管理多只宠物档案（品种/年龄/性格/饮食禁忌/医疗信息/既往病史），以便喂养师准确照顾；异宠（兔/鸟/仓鼠/龟）也有对应档案。
- 作为宠主，我想选择宠物、服务时间、服务内容并支付，以便完成上门喂养预约。
- 作为宠主，我想勾选附加服务（梳毛/剪指甲/驱虫/生骨肉备餐/喂药等）逐项计费，以便获得精细化照料。
- 作为宠主，我想在宠物突发不适时预约应急上门或紧急送医协助，以便第一时间处理。
- 作为宠主，我想在下单时签署上门授权协议，以便明确门锁/钥匙授权与责任边界。
- 作为宠主，我想在喂养师进门前、离开时收到消息提醒，以便随时知晓家中情况。
- 作为宠主，我想查看每次服务的 AI 图文喂养报告与全程录像回看，以便确认宠物被妥善照顾。
- 作为宠主，我想在服务过程中通过专属服务群实时了解宠物状态（图文播报），以便安心。
- 作为宠主，我想在订单完成后评价喂养师，以便维护服务质量。
- 作为宠主，我想在「我的订单」里按全部/进行中/已完成/已取消筛选并回看服务流转，以便随时掌握进度。
- 作为宠主，我想在会员中心看清权益并开通月度或年度会员，以便长期下单更省。
- 作为宠主，我想在领券中心主动领取优惠券、用券码兑换，并在支付页自动抵扣，以便不被"必须后台发给我"限制。
- 作为宠主，我想在消息通知里集中查看进门/离门提醒、异常预警与报告推送，以便不漏关键节点。

**喂养师端**
- 作为喂养师，我想实名认证并通过分级审核，以便获得接单资格。
- 作为喂养师，我想收到派单通知并在限时内接/拒单，以便自主安排工作。
- 作为喂养师，我想通过打卡、checklist、拍照完成服务并全程录像上传，以便服务有据可查。
- 作为喂养师，我想按量化标准执行服务（陪玩≥10分钟、清洁食具、彻底清理猫砂及周边），以便保证质量一致。
- 作为喂养师，我想在宠主付费时开启服务直播，以便增强透明与信任。
- 作为喂养师，我想在当天多单时看到 AI 推荐的最优路线，以便减少通勤。
- 作为喂养师，我想查看接单记录、收入与评分，以便了解收益与口碑。
- 作为喂养师，我想在「我的档案 · 编辑」维护手机号、紧急联系人与常驻地址，并只读查看认证等级、抽成、账号状态与每日档期，以便资料始终是平台派单依据。
- 作为喂养师，我想在档期页看到后台设定的每日档期同步结果，以便知道今天能不能接单。

**运营端（后台）**
- 作为客服，我想用 AI 客服自动回复高频问题、人工接管复杂问题，以便高效响应。
- 作为调度，我想查看 AI 派单结果并人工改派，以便兜底异常。
- 作为运营，我想审核喂养师入驻、监控订单与数据，以便保障服务质量与业务健康。
- 作为运营，我想受理 24h 应急订单、维护就近合作医院资源并跟进送医，以便处理紧急情况。
- 作为运营，我想自定义会员套餐（名称 / 周期 / 价格 / 宠主端展示 / 状态）并新增任意档位，以便随时调价而不改代码。
- 作为运营，我想自定义喂养师等级、达标条件、平台抽成与派单权重，并能试算抽成、模拟晋升，以便规则可解释、可回滚。
- 作为运营，我想在一个判定器里看到每位候选喂养师的淘汰原因与得分，并一键派给 Top1，以便 AI 结论可复核、可干预。
- 作为运营/客服/财务，我想按路由进入 16 个模块，用搜索、筛选、分页、批量操作处理数据，并在数据字典里查字段来源，以便多人协作不靠口头对齐。
- 作为财务，我想按结算周期查看抽成与应结算金额并标记结算，以便对账。

### 验收标准（Acceptance Criteria）

**核心闭环（下单 → 派单 → 上门 → 报告 → 评价）**
- 宠主可完成"选宠物 → 选时间 → 选服务 → 选附加服务 → 签署协议 → 支付"全流程，支付成功率 ≥ 99%。
- 下单后 60 秒内完成 AI 派单并推送喂养师（喂师拒单后自动派下一位，直到有人接单或超时转人工）。
- 喂养师接单后，进门前触发消息提醒、进门后全程录像上传、离开时触发消息提醒，三项均 100% 触发。
- 每次服务完成后，AI 生成喂养报告并推送宠主，报告覆盖率 100%。
- 订单完成后宠主可评价喂养师，评价数据进入喂养师评分。
- 每单建立专属服务群（宠主+喂养师+客服），服务中支持图文播报。

**应急/送医（MVP 纳入）**
- 宠主可预约 24h 应急上门与紧急送医协助。
- 喂养师执行中触发异常时，推送就近合作医院清单 + 送医引导。
- 应急订单由后台运营受理并跟进，服务时效达标（目标 1 小时内响应上门）。

**AI 智能派单**
- 判定按固定顺序执行，任一硬过滤不通过即淘汰并写明原因：① 账号状态（停用直接淘汰）→ ② 当日是否休息 → ③ 常驻/当日地址与服务半径的距离 → ④ 上门时间是否落在当日可服务时段 → ⑤ 当日容量是否用尽 → ⑥ 类目与高风险资质（遛狗 / 喂药）→ ⑦ 排除该宠主曾给过 1–2 星的喂养师 → ⑧ 熟悉宠物 / 距离 / 等级评分 / 当前负载评分。
- 现行总分 100 分：同一宠物完单历史 40 分；服务半径内距离线性 0–30 分；等级配置权重与平滑评分各占等级项一半，共 20 分；在途订单负载 10/(1+订单数)，最高 10 分。评分使用 5 条 4 星先验平滑，详见 v1.5 附录；四大分项权重当前固定，等级配置仅影响等级项。
- 特殊需求（喂药/攻击性宠物/多宠）只派给认证过相应能力的喂养师；等级下调或资质过期自动冻结高风险类目派单。
- 派单结果附带可解释的"派单理由"，调度可在后台查看并改派，**宠主端可查看派单理由**（差异化信任点）。
- 原型判定器展示规则评分与淘汰原因，Top1 按钮为规则模拟。当前业务由后端每 10 秒扫描待派订单并调用大模型；模型只能在合格名单中结合备注与服务偏好选择。成功后进入 `PENDING_ACCEPT`、60 秒接单；人工派单作为兜底。
- 派单读取档案、当日档期、订单快照、评价与履约记录；影响准入或评分的字段变化后重新计算。姓名等非评分字段变化不要求改变结论。

**AI 智能客服**
- 自动回复高频问题（价格/范围/流程/改期/退款），准确率 ≥ 90%。
- 当前用户可主动联系人工；等待人工与已接管期间消息进入人工会话，恢复 AI 后开启新会话。三轮未解决自动升级仍为后续目标，不能作为当前已交付能力。

**AI 智能喂养报告**
- 输入喂养师 checklist + 照片 + 备注，自动生成结构化图文报告。
- 语气"温暖 + 克制"，不做医疗断言。
- 轻微异常仅提示，明显异常（拒食/呕吐/受伤）触发即时预警推送 + 通知客服。

**安全机制**
- 全程录像上传云端，宠主可在订单详情回看。
- 进出消息提醒 100% 触发，含时间戳。

**会员与定价**
- 宠主端会员中心展示身份、权益清单（服务费 9 折 / 优先派单 / 专属客服 / 生日礼遇）、月度 ¥29 / 年度 ¥199（年度立省 ¥149、赠 2 张 ¥20 券）与开通/续费按钮；权益随后台开关实时变化。
- 运营后台可新增任意套餐（名称 / 周期月数 / 价格 / 宠主端展示名 / 状态），价格支持 0.01–9999、两位小数。
- 保存自定义套餐后，宠主端会员中心与开通按钮同步更新；已支付订单按下单时价格，不受调价影响。
- 会员套餐与权益变更写入操作日志。

**优惠券（双通道）**
- 发放类型分「后台直接发放」与「用户主动领取」，共用同一券模板，差异只在发放链路。
- 领取必须走 7 步校验（状态 / 时间窗 / 人群 / 限领 / 库存 / 风控 / 入账），失败给出具体淘汰原因与后续动作。
- 领取或直发成功后，宠主端券包、后台已领取数、领取流水、支付页抵扣四处一致。

**喂养师档案与等级规则**
- 档案四段（基本信息 / 资质结算 / 常驻地址 / 每日档期）同屏可编辑，一次保存全端同源。
- 等级规则支持新增等级、达标条件（完单 / 评分 / 重大投诉）、抽成（0–50%）、派单权重（0–100%），并提供抽成试算与晋升模拟。
- 规则保存后同步档案、详情、财务结算、服务价格、喂养师端收益页；进行中订单按下单时抽成结算。

**运营后台通用能力**
- 16 个模块均可通过侧栏点击进入，URL 写入 `#/admin/<模块>`，支持浏览器前进/后退、刷新保持与深链直达（含 `?edit=` / `?focus=` 参数）。
- 列表类模块统一具备搜索、筛选、分页、批量选择与批量操作（如批量停用 / 启用 / 发券）、空态提示。
- 关键配置（会员套餐、等级抽成、券规则、服务价格、消息模板）保存即生效并写入操作日志；日志可按本次操作过滤。
- 数据字典覆盖会员、喂养师、订单等核心字段的类型 / 来源 / 同步端，字段变更留痕。

### 非目标（Non-Goals）

- **不做 App**（2.0 再评估）
- **不做**宠主与喂养师的"自由抢单市场"或**自由报价撮合制**（保持自营品质可控）
- **不做**宠物医疗诊断（AI 报告只做事实描述，不做医疗建议）
- **不做**宠物健康趋势分析（阶段二）
- **不做**寄养、美容、洗护、善后等其他宠物服务（先聚焦"上门喂养"）
- **不做**多个独立后台子系统：运营后台保持单一入口 + 16 模块路由，不为单个模块拆独立站点
- **不做**喂养师自填档期：每日档期以后台档案为准，端侧只读展示，避免派单依据与履约能力不一致

## 3. AI System Requirements（AI 系统需求）

### AI 能力清单（阶段一）

| 能力 | 说明 |
|------|------|
| A. AI 智能派单 | 后端准入与低星排除 + 40/30/20/10 分项评分 + 大模型在合格名单中结合备注和偏好选择，输出解释；失败重试、人工兜底 |
| B. AI 智能客服 | 高频问答 + 转人工兜底，稳定维持自助解决率 |
| C. AI 智能喂养报告 | 结构化图文报告生成，异常即时预警 |
| D. AI 上门路线推荐 | 多单路线规划 |
| E. AI 差评预警与工单归类 | 评价语义识别差评并预警，投诉工单按类型 / 来源归类，驱动 24h 响应 SLA |

> 原型用于解释交互；实际派单准入、评分、并发校验及状态以 Spring Boot `DispatchServiceImpl` 为准，现行口径见 v1.5 附录。

### AI 技术栈（独立 Python AI 服务）

> 架构决策：AI 能力独立为 **Python 服务**，与 Java 业务后端分离，通过内部 API 通信。理由：Python 是 AI 生态第一语言，LangChain/LangGraph 及模型 SDK 均最成熟，独立服务避免污染 Java 业务、可单独扩缩容。

| 模块 | 技术选型 | 说明 |
|------|----------|------|
| AI 服务语言 | **Python**（独立服务，与 Java 业务后端分离） | 内部 HTTP/gRPC 通信 |
| AI 应用框架 | **LangChain**（需要多步 Agent 时再引入 LangGraph） | Python 生态成熟，未来可平滑扩展 |
| 大模型调用 | OpenAI / Claude / 国内大模型（DeepSeek、通义、文心）可替换 | 通过 LangChain 抽象层切换供应商，降低单点依赖 |
| 智能派单 | Spring Boot 资格规则 + 固定分项评分 + OpenAI 兼容大模型调用 | 模型只选白名单；Python 派单建议接口尚未接入此业务链 |
| 智能客服 | RAG（检索增强生成）+ 知识库（FAQ/服务规则） | 基于 PostgreSQL + pgvector 做向量检索 |
| 喂养报告 | 大模型文本生成 + 模板约束（JSON Schema 结构化输出） | 保证报告结构一致、语气可控 |
| 路线推荐 | 地图 API（高德/腾讯地图）+ 简单路径规划 | 多单 TSP 近似求解 |
| 向量检索 | PostgreSQL + pgvector 扩展 | 复用现有 PGSQL，无需额外向量库 |
| 异步任务 | 消息队列（如 RabbitMQ / RocketMQ） | 派单、报告生成等耗时任务异步化 |

### 评估策略（Evaluation Strategy）

- **派单质量**：人工改派率 ≤ 10% 作为核心指标；抽样回溯派单理由与最终匹配的合理性。
- **客服准确率**：构建 50 条高频问题测试集，AI 回答准确率 ≥ 90%；错误答案回流修正知识库。
- **报告质量**：抽样 100 份报告人工评审，检查结构完整性、事实准确性、语气合规（无医疗断言）；明显异常识别召回率 ≥ 90%。
- **路线推荐**：对比 AI 推荐路线与喂养师实际出行时间，通勤时间下降 ≥ 15%。

## 4. Technical Specifications（技术规格）

### 架构概览（Architecture Overview）

```
[官网 Vue3]  [小程序 uni-app]  [后台 Vue3+ElementPlus]
        │              │                │
        └──────────────┼────────────────┘
                       ▼
              [API 网关 / 鉴权]
                       ▼
          [Java SpringBoot 业务后端]
            订单/用户/喂养师/财务/消息
                │            │
                │            │ 内部 API（HTTP/gRPC）
                │            ▼
                │   [Python AI 服务（LangChain）]
                │    智能派单 / 智能客服(RAG) /
                │    喂养报告 / 路线推荐
                │            │
                ▼            ▼
    [PostgreSQL + pgvector]   [大模型 API]
    [对象存储:录像/照片]
    [消息队列]  [地图 API]  [微信支付]
```

> 职责边界：Java 服务负责业务数据、订单状态、鉴权、财务；Python AI 服务提供客服 RAG，以及报告、派单建议、路线排序接口；当前业务派单由 Spring Boot 直接调用兼容模型服务，客服由 Spring Boot 代理 Python。报告与路线的完整业务接入仍待联调。

### 集成点（Integration Points）

| 集成 | 说明 |
|------|------|
| 微信小程序 | 登录、微信支付、消息推送（订阅消息） |
| 地图服务 | 高德/腾讯地图：定位、距离计算、路线规划 |
| 对象存储 | 全程录像、照片的云端存储（建议设回看有效期，如 7 天） |
| 大模型 API | 由 Python AI 服务统一调用（可替换供应商） |
| Python AI 服务 | Java 业务后端经内部 API（HTTP/gRPC）调用 |
| 支付 | 微信支付（小程序内） |
| 消息推送 | 微信订阅消息（进/出门提醒、异常预警、报告通知） |

### 安全与隐私（Security & Privacy）

- **全程录像数据**：涉及宠主住宅隐私，需加密存储、访问鉴权（仅订单相关方可看）、明确保留期限、可一键删除。
- **授权协议**：下单时电子签署上门授权协议，明确门锁/钥匙授权范围与责任边界。
- **宠物健康数据**：仅做事实记录，不做医疗判断；报告避免医疗性断言。
- **个人信息**：实名信息（身份证）按《个人信息保护法》最小化采集、脱敏存储。
- **责任保障**：配套平台责任险 / 宠物意外险机制（待落地）。
- **权限控制**：后台按角色（运营/客服/调度/财务）分离权限。

2. **AI 派单"可解释理由"**：竞品均为人工/撮合，暖爪附带理由，宠主可查看。
3. **异常主动预警**：拒食/呕吐/受伤即时推送，竞品靠人工观察易漏报。
4. **进/出门实时提醒**：100% 触发含时间戳，强化"全程可见"心智。

### 不可抄与风险

- **不可抄**：自由报价撮合制、宠托师收认证费、全国快速铺开、多元业务（洗护/善后等）。
- **风险**：滴滴等巨头已试点"上门喂遛"（统一接单/派单/购险/处理纠纷），路线与暖爪高度重合，须以 AI 差异化抢时间窗口。

## 附：喂养师档案编辑（v1.3 补充）

> **归属原则**：常驻地址、经纬度、服务半径、交通方式、周一至周日逐日档期，以及认证等级、抽成、账号状态，均属于**喂养师个人档案**，不拆成独立模块。原型中原「服务地址 · 每日档期设定」独立卡片已收编为运营后台「喂养师档案 · 编辑」全宽面板（09-A）。

### 档案字段（四段同屏）

| 段 | 字段 | 可编辑端 | 派单 / 业务用途 |
| --- | --- | --- | --- |

### 编辑与保存规则

- **一次提交**：点「保存档案」把四段一起写入；另保留「保存地址与档期」只提交 ③④ 段的快捷入口。切换喂养师（列表行「编辑档案」/ 详情卡「✎ 编辑档案」/ 编辑器内搜索定位 / 上一位·下一位 / 深链）时四段字段整体刷新。
- **校验**：姓名非空且 ≤12 字、手机号 `1[3-9]\d{9}`、抽成 0–50%（两位小数）、擅长类目至少 1 个、备注 ≤60 字、经纬度在深圳范围、服务半径 0.5–50km、7 天时段格式 `HH:MM` 且开始早于结束、容量 0–20。任一不通过即拦截并给出第一条具体原因，不写入。
- **变更预览**：保存前列出「旧值 → 新值」，并解释下游影响——停用 → AI 直接淘汰；等级 → 派单权重与高风险类目；抽成 → 下个结算周期生效（进行中订单按下单时抽成）；地址 / 半径 / 档期 → 距离与时段判定。支持「放弃修改」二次确认还原。
- **保存联动**：喂养师列表行、档案详情卡、喂养师端「我的档案」、✦ AI 派单判定、财务结算、操作日志、localStorage 同源更新。

### 端侧与入口

- **运营后台：列表 → 编辑的主从视图**。默认只显示列表与详情，编辑器不占页面；点列表行「编辑档案」或详情卡「✎ 编辑档案」进入全宽编辑视图，编辑期间列表、详情与等级规则收起，避免同屏重复。编辑器顶部固定「← 返回列表 / 当前等级·状态·抽成 / 搜索定位 / ‹ › 顺序切换」，下方用四段导航替代人员标签；返回后恢复列表并高亮刚编辑的那一行。
- **侧栏只保留一级模块**：16 条路由不再挂「↳」子项。档案编辑、等级抽成、地址档期、AI 派单判定都在各自模块内定位，不重复出现在导航里。
- **深链**：`#/admin/sitter?edit=<工号>`（兼容 `?focus=profile&sid=<工号>`）直接打开该喂养师的编辑视图。
- **喂养师端**：新增「我的档案 · 编辑」屏（AI 同源提示、基本信息 / 常驻地址可编辑、等级 / 抽成 / 状态 / 档期只读、保存、生成后台档案深链）；个人主页「编辑」直达该屏，不再是「申请入驻」。
- **等级与抽成规则**仍为平台级配置（09-B），不属于个人档案；个人档案只引用已启用等级与对应抽成。

### 为什么不放「人员下拉 / 快捷标签」

- 喂养师规模是**上百人**，下拉与人员 chip 都是全量枚举：找一个人要先滚长列表，和列表页已有的搜索 / 筛选 / 分页重复，人越多越难用。
- 采用**列表定位 → 单人编辑**：在列表页用搜索 / 筛选 / 分页把人定到 1 个，再进入编辑视图；定位成本不随人数增长。
- 编辑器内只保留两种轻量切换：**关键词定位**（姓名 / 工号 / 区域，输入即出候选，最多 6 条）与**上一位 / 下一位**（连续核档期场景），不承载全量名单。
- 侧栏同理：一级模块点进去就能用，不再为同一模块挂多个「↳」子入口。

### 验收点

- 任一档案字段改动后，变更预览能列出改动并给出对应下游影响说明
- 保存后列表行、详情卡、喂养师端、AI 判定、日志五处状态一致；停用 / 改等级 / 改地址能立刻改变 AI 派单结论
- 校验失败不写入；「放弃修改」能还原到上次保存值且不破坏 7 天档期
- 移动端保存与后台同源，且不清空每日档期；只读项不可在端侧修改

### 双端智能客服与人工切换

- 宠主常见问题：订单与派单、服务范围、服务价格、特殊照护；喂养师常见问题：接单与档期、服务打卡、收益问题、遛狗照护。支持快捷提问、文本发送、历史消息、发送中禁用和错误提示。
- 角色来自 Spring Boot 登录态，不允许客户端自选角色绕过知识范围；会话按发起人隔离。兼容字段 owner_id 实际存发起人账号 ID。
- WAITING_HUMAN 当前表示可由 AI 回复的通用会话；主动联系人工后变为 HUMAN_REQUESTED，后台接管为 HUMAN。两种人工状态下发送消息不调用 AI；恢复智能客服创建 / 返回新会话 ID，并清空当前消息展示。
- 通用会话支持 2000 字内文本。订单关联服务群走消息接口，与智能客服分开；人工等待期间可留言，不能模拟成已成功处理业务。
- 当前客服不查询实时订单、价格、会员、优惠券、喂养师位置或医院营业状态，也不执行退款、取消、改期、投诉或送医；无依据时明确无法确认，引导业务页面或人工核实。
- 验收：双方常见问题按角色呈现；跨账号不能读取会话；转人工后 AI 不抢答；恢复 AI 返回新会话；空白消息不提交；错误后可重试；订单群消息不进入知识问答。

### 知识库范围、引用与发布

- 当前语料为 11 篇、73 条问答，内容覆盖预约、费用、售后、服务记录、喂养师操作、地址排错、照护交接、异常安全、隐私边界、任务排错、媒体报告通知。
- 仅从 5.ai/knowledge/documents 直属 Markdown 加载；必须 published 且 reviewed_by 非空，draft / archived、planning 和 evaluation 不进入线上索引。技术核对不等同于运营、兽医或法务审批。
- embedding 与关键词检索按 OWNER / SITTER 过滤后融合排序，最多返回 5 条；短追问可使用上一条用户问题，历史 AI 答复不当作证据。回复应标注实际来源标题、小节、版本，不得编造引用。
- 语料、模型或服务地址变化后重新入库并重启；启动校验语料指纹和段数，索引事务替换失败保留旧索引。当前没有热更新或后台知识管理页面。
- 公共知识库不存真实订单、地址、门锁凭证、证件或个人病史；模型密钥只在服务端。Python 面向可信后端，以内部 Key 鉴权，不直接接受客户端登录令牌。
- 验收：已存在 28 道检索评测题用于前五条命中、角色隔离、无答案返回；向量检索通过不代表回答准确率通过，需另验来源引用、无依据拒答及医疗 / 政策边界。50 条问答与 90% 准确率保留为上线目标。

### 服务地址与服务偏好

- 地址列表支持新增与编辑；输入至少 2 字搜索地点，选择提示项后补齐区、详细地址、经纬度；无坐标提示项可继续地理编码，定位失败引导搜索。保存前补全联系人、手机号、楼栋门牌和有效坐标。
- 地址和喂养师位置统一坐标口径；保存后的地址用于后续预约，已创建订单使用地址快照。搜索中、无结果、定位拒绝、解析失败与保存失败均应有明确反馈。
- 喂养师服务经验与偏好 servicePreferences 最多 1000 字，在入驻和档案编辑中填写；与普通档案备注分开。可描述大型犬、怕生宠物及明确不承接情况，不能替代认证或医疗资质。
- 订单特殊备注与候选人的偏好一并传给派单模型；模型应在理由中说明相关经验和限制，无相关信息时不得推测。等级、抽成、状态、每日档期仍由后台维护。
- 原型地址与偏好使用独立本地演示数据，地址可保存 / 编辑；偏好按工号保存并在同一画布的两端展示。此演示不写入真实账号或数据库。

### 派单算法与失败边界

1. 后端校验账号、资质、休息日、时段、半径、容量和时间冲突；排除该宠主曾给过 1–2 星的喂养师。距离使用订单地址快照和喂养师当日档期位置，否则用常驻位置，不使用实时位置或道路距离。
2. 总分＝同宠历史项（有完单为 40，否则 0）＋30×max(0,1−距离/半径)＋20×(0.5×等级权重/100＋0.5×平滑评分/5)＋10/(1+在途订单数)。平滑评分＝(评价总分+20)/(评价数+5)，在途状态为 PENDING_ACCEPT / ACCEPTED / SERVICING。无评价时使用 4 星先验。
3. 大模型仅从后端白名单选择，读取订单备注、候选分数、服务偏好并返回解释；不要求永远选规则 Top1。写入前按订单、喂养师顺序加锁并重新验证准入，不能绕过资质或超容量。
4. 每 10 秒扫描新订单与待派单订单；模型不可用或结果非法时保留原状态，下轮重试，不伪造派单成功，不静默替换成规则派单。无候选由运营处理；拒单或 60 秒接单超时后回到待派状态再选。
5. 后端保留按综合分直接自动派单接口及人工派单；后台 UI 现有操作入口以实际权限与页面为准。原型 Top1 为规则交互演示，缺少真实历史明细时同宠历史、评价数、在途负载按 0 处理；可在「历史记录演示」中选择同宠熟悉人选或历史低星人选，验证 40 分加成及准入排除。

验收覆盖无候选、历史低星排除、同宠熟悉度、评价先验、负载变化、模型选择越界、故障重试、并发重验、拒单与超时、偏好匹配理由。上述为验收要求，本次文档同步不声称已复跑完整业务测试。
